# 6.1절 영어 회화 연습 에이전트 분석

출처: 『문제 해결을 위한 AI 에이전트 설계』(한빛미디어) 6.1절, p140~p155. 2026-11-17에 캡처 17장(p141은 두 장)을 한 번 읽고 목적·흐름·프롬프트·상태·평가의 원칙과 결정만 자기 말로 정리했다. 원문 문장·프롬프트 본문·코드는 옮기지 않았다. 아래 수치·모델명은 책 예제의 값이며 ai-ps `/talk`는 다른 값을 쓴다(`design.md`).

## 1. 페이지별 핵심

STT·TTS는 **도구가 아니라 파이프라인**: 매 턴 반드시 거치는 고정 단계라 LLM이 호출 여부를 판단할 일이 없다. "음성 입력 → STT(항상) → LLM(대화) → TTS(항상) → 음성 출력" |
| p143 | **운영의 제약**: 실시간성이 가장 어려운 제약(사람 대화는 0.2초 안팎에 반응, 파이프라인은 세 API 호출 지연이 누적). 비용은 토큰(LLM)+오디오 분량(STT)+텍스트 분량(TTS)으로 세 종류가 함께 늘지만 원어민 과외 대비 저렴해 결정적 제약은 아님. **실패 허용도는 대화에는 높고 교정에는 낮다**: 맞는 문장을 틀렸다고 하거나 잘못 교정하면 해가 되므로 "확신이 없으면 교정하지 않는다"를 시스템 프롬프트에 반영. 그림 6-1 = 4분면 요약(출력: 중간 온도·대답+교정 구조화·짧은 이유·멀티모달 / 실행: 멀티턴·도구 불필요·고정 파이프라인 / 운영: 실시간성 매우 중요·비용 수용 가능·대화 실패 허용 높음·교정 실패 허용 낮음 / 과제: 세 모달리티 연결·응답 지연 관리·신뢰할 수 있는 교정 피드백) |
| p144 | 개발 환경: 설치가 간단한 오디오 라이브러리 2개(녹음·재생용, 파일 입출력용) 선택. 첫 실행 시 OS 마이크 권한 허용 필요. 녹음 함수: 샘플레이트 **16 kHz 모노 16비트**(음성 인식에는 충분), 고정 길이 녹음 후 wav 저장 |
| p145 | 재생 함수는 파일 헤더의 샘플레이트를 그대로 쓴다. **단순화**: 녹음 길이를 5초 고정(발화 끝 감지는 실시간 분석 로직이 필요해 예제가 복잡해짐). 음성 인식: 오디오 파일 → 텍스트, 전용 transcription 엔드포인트 호출(채팅과 같은 클라이언트 객체로 다른 종류의 모델 호출) |
| p146 | STT 모델 선택 근거: 이전 세대보다 정확도 높고 집필 시점 분당 약 0.003달러로 저렴. **언어를 영어로 고정**하면 인식 정확도가 오르고 서툰 발음도 영어 전제로 해석. 튜터 시스템 프롬프트 구성: 페르소나(친절한 영어 회화 튜터) / **대화 규칙**(항상 영어·구어체, 응답 끝에 가벼운 질문, 학습자 수준에 맞춤, 두세 문장 이내) / **교정 규칙**(명백한 문법 오류·부자연스러운 표현만, 이유는 한국어로 짧게, 사소하거나 확신 없으면 교정 금지, STT 오류로 보이는 것은 교정 대상 아님) / **응답 형식**(JSON: 영어 응답, 교정 내용+이유 또는 null, 더 자연스러운 표현 또는 null) |
| p147 | 프롬프트 의도 3가지: ① 짧은 응답+끝 질문(학습자가 말하게 하기) ② 교정은 보수적(교정 실패 허용도 낮음의 반영, STT 오류 제외도 같은 맥락) ③ JSON 구조화(대답은 스피커로, 교정·제안은 화면으로 — 5장의 묘사+상태 변화 단일 JSON과 같은 접근). 응답 함수: json_object 모드, reasoning 없음, **temperature 0.7**, assistant 응답을 히스토리에 그대로 추가, 필수 키가 빠지면 **되묻는 기본 문장으로 대체**하는 방어 한 줄 |
| p148 | json_object가 보장하는 것은 문법적으로 유효한 JSON까지이며 특정 키의 존재는 보장하지 않는다(키 강제는 8장 예고). 0.7은 게임 0.9보다 낮고 요약 0.3보다 높다. 음성 합성: 전용 speech 엔드포인트, voice 선택(취향), **instructions**로 말투 지시(또렷하고 적당한 속도의 영어 튜터; 수준이 낮으면 천천히). "텍스트 내용은 LLM이, 말투는 TTS가" 역할 분담. instructions는 신세대 TTS 모델 기능 |
| p149 | 출력 형식을 **wav**로 지정한 이유: 압축 포맷은 디코딩이 필요하지만 wav는 바로 재생. 메인 루프: system 메시지 → **튜터가 먼저 인사**(세션 시작을 알리고 가벼운 주제로 시작하라는 숨은 user 지시문) → 인사 출력·재생 → 루프: 종료어 처리 → 녹음 → STT → 인식 텍스트 표시 → user 메시지 추가 → 튜터 응답 → 교정 표시 |
| p150 | 제안 표시 → 튜터 응답 표시 → TTS 재생. 루프 종료 후 보고서 생성. 루프 구조는 5장 게임과 닮았고 입력 앞에 녹음·STT, 출력 뒤에 TTS·재생이 붙은 점만 다르다. **교정과 제안은 음성으로 읽지 않고 화면에만** 표시(의도적: 대화 중 한국어 문법 설명은 흐름을 끊는다. 좋은 튜터는 대화를 이어 가며 교정은 가볍게 짚고 넘어간다). 실행 예: 시제 오류에 교정+자연스러운 표현 제안 |
| p151 | 실행 예 계속: 문제없는 발화에는 교정 없이 대화만 이어짐("확신 없으면 교정하지 않는다"의 동작). **세션 보고서**: 대화 중 가볍게 넘어간 것을 끝난 뒤 차분히 복습. system과 시작 지시문을 제외한 히스토리를 "학습자:/튜터:" 줄로 정리해 한국어 보고서 요청(① 반복된 실수 패턴 ② 잘 사용한 표현 ③ 다음 연습에서 시도할 표현·주제, 터미널 출력이라 마크다운 없이) |
| p152 | 보고서 호출은 reasoning 없음·**temperature 0.3**(5장 히스토리 요약과 같은 이유: 사실을 정확히 정리). 대화 0.7·보고서 0.3처럼 **한 시스템 안에서 용도별 온도**. 히스토리에 튜터의 JSON 응답이 그대로 있으므로 교정 내역도 보고서 LLM에 전달되어 실수 패턴을 뽑을 수 있다. 보고서 출력 예(실수 패턴·잘한 표현·다음 과제) |
| p153 | 그림 6-2 전체 구조: 학습자 발화(마이크) → 녹음(1.0) → STT(2.0) → LLM 영어 튜터(3.0, 대화+교정 JSON, 0.7) → reply/correction 분리(1.0, correction은 화면 표시·기록) → TTS(2.0) → 스피커 재생·다음 발화 대기. 세션 종료 시 대화 기록 → 학습 보고서. 세 패러다임이 각자 잘하는 일을 맡는다 |
| p154 | 지연 측정(예제 환경): STT 약 1초, LLM 1~3초, TTS 1~2초 → 합 3~6초 + 녹음 5초 고정. 이는 구현 실수가 아니라 **파이프라인 구조의 본질적 한계**(각 단계가 이전 출력을 입력으로 받아 병렬화 불가). **스트리밍**으로 체감 지연은 줄일 수 있다(첫 조각이 대개 1초 안). 그러나 튜터 응답은 reply·correction을 담은 **JSON이라 끝까지 받아야 파싱**할 수 있어 바로 붙이기 어렵다(5장이 스트리밍을 권장하고도 구현하지 않은 이유와 같다). 구조화 응답에는 "보일 부분과 처리할 부분을 나누는 설계"가 먼저 필요 |
| p155 | 파이프라인 한계를 넘는 두 방향: ① **오디오를 직접 이해·생성하는 통합 오디오 LLM**(Chat Completions에서 오디오 입·출력; 세 호출이 하나로, 톤·감정·발음 정보가 보존되어 발음 피드백 가능) ② **Realtime API**(상시 연결로 음성 스트리밍, 브라우저는 WebRTC·서버 간은 WebSocket, 1초 미만 지연, 끼어들기 처리; 오디오 모델은 세대 교체가 빨라 공식 문서에서 현재 모델 확인 권장). 그럼에도 파이프라인을 먼저 만든 이유: 각 단계 입출력이 보여 디버깅·학습에 유리, 중간 텍스트가 있어 교정 표시·세션 기록이 자연스럽다. **학습·디버깅에는 파이프라인, 저지연 프로덕션에는 통합형**. 정답이 아니라 운영 제약에 따른 선택 |

## 2. 설계 결정 요약(책)

### 출력의 성격
- 자연스러운 일상 대화, 극적 창의성 불필요 → 온도 중간(예제 0.7).
- 한 응답에 **대답(음성용)과 교정·제안(화면용)** 을 구조화해 담는다. 5장의 "서술+상태 변화 단일 JSON"과 같은 접근.
- 교정에는 짧은 이유(한국어). 근거 추적 수준의 설명 가능성은 불필요.
- 멀티모달(음성 입·출력)이 본질.

### 실행의 구조
- 사용자가 주도하는 멀티턴. 자율 루프 없음. 튜터가 먼저 인사한다.
- STT·TTS는 도구가 아니라 **고정 파이프라인 단계**. LLM 판단이 필요 없는 외부 기능은 도구로 만들지 않는다.
- 응답 JSON의 필수 키 누락은 되묻는 기본 문장으로 방어(상태 오염이 아니라 대화 지속이 목표).

### 운영의 제약
- 실시간성이 핵심 제약: 세 호출의 지연이 누적(예제 3~6초 + 고정 녹음 시간). 체감을 줄이는 수단은 스트리밍이지만 JSON 응답과 충돌.
- 비용은 토큰+오디오 분량+텍스트 분량. 수용 가능.
- **대화 실패 허용 높음 / 교정 실패 허용 낮음** → "확신 없으면 교정하지 않는다", STT 오류로 보이는 것은 교정하지 않는다.

### 핵심 과제와 책의 대응
| 과제 | 대응 |
|---|---|
| 세 모달리티 연결 | STT→LLM→TTS 파이프라인. 중간에 텍스트가 있어 표시·기록이 자연스럽다 |
| 응답 지연 관리 | 녹음 고정 길이는 단순화. 스트리밍은 구조화 응답과 충돌. 근본 해법은 통합 오디오 모델 또는 Realtime API(책은 설명만 하고 구현하지 않음) |
| 신뢰할 수 있는 교정 | 보수적 교정 규칙, 교정은 화면에만, 세션 끝에 보고서로 복습 |

## 3. 상태·세션 아이디어

- 책의 상태는 **메시지 배열 하나**(system → 시작 지시 user → user/assistant 교대). assistant 내용은 JSON 문자열 그대로라 교정 내역이 히스토리에 남고 보고서 입력이 된다.
- 화면 표시용으로 분리할 것: 인식 텍스트(학습자), 교정, 제안, 튜터 대답.
- 세션 종료 시 system과 시작 지시문을 뺀 기록을 "학습자:/튜터:" 줄로 평탄화해 보고서 프롬프트에 넣는다.
- 히스토리 길이 관리는 6.1에 없다(5.1.1의 요약 기법을 적용할 수 있다).

## 4. 프롬프트 구성 원칙

1. 페르소나 1줄 → 대화 규칙 → 교정 규칙 → 응답 형식(JSON 필드와 의미, null 허용) 순서.
2. 대화 규칙의 핵심: 항상 영어·구어체, **두세 문장**, 끝에 가벼운 질문, 학습자 수준 추종.
3. 교정 규칙의 핵심: 명백한 오류만, 이유는 한국어로 짧게, **사소하거나 확신 없으면 교정하지 않음**, STT 오류 의심은 제외.
4. 세션 시작은 숨은 user 지시문으로 "인사하고 가벼운 주제로 시작"을 요청한다.
5. 보고서 프롬프트는 별도 1회 호출(낮은 온도), 항목 3개 고정, 출력 매체에 맞는 서식 지시.
6. TTS에는 **말투 지시**를 따로 준다(내용은 LLM, 말투는 TTS).

## 5. 평가·관찰 포인트(책이 보여 준 것)

- 실행 예로 확인한 동작: 시제 오류 → 교정+자연스러운 표현 제안; 문제없는 발화 → 교정 없음.
- 보고서 예: 반복 실수 패턴(과거형), 잘한 표현(이유 덧붙이기), 다음 과제(과거형 연습·경험 표현).
- 지연 실측을 단계별로 적어 두고 어디가 병목인지 보는 것이 평가의 출발점.

### 다시 볼 필요가 없게 기록한 것(책 예제 값, 참고용)
- 녹음: 16,000 Hz·1채널·int16·wav, 5초 고정, 엔터로 시작.
- STT: transcription 엔드포인트, `language="en"`, 모델은 집필 시점 소형 transcribe 모델(분당 약 0.003달러).
- 튜터: json_object, reasoning 없음, temperature 0.7, 응답 키 3개(`reply`, `correction`, `better_expression`; 뒤 둘은 null 허용), 필수 키 누락 시 "다시 말해 달라"는 기본 문장.
- TTS: speech 엔드포인트, voice는 취향(예제는 coral), instructions로 또렷·적당한 속도 지시, 출력 wav.
- 보고서: user 1개 프롬프트, 항목 3개, reasoning 없음, temperature 0.3, 마크다운 없이.
- 지연: STT ~1초, LLM 1~3초, TTS 1~2초, 합 3~6초 + 녹음 5초.
- 책의 모델명(채팅·STT·TTS)은 집필 시점 값이며 ai-ps 키에서 허용되는 모델과 다르다. 기록하지 않는다.
