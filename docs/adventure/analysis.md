# 5.1절 텍스트 어드벤처 분석

출처: 『문제 해결을 위한 AI 에이전트 설계』(한빛미디어) 5.1절, p120~p131. 2026-11-17에 캡처 14장(p120·p121은 보조 캡처 포함)을 한 번 읽고 설계 원칙과 결정만 자기 말로 정리했다. 원문 문장·프롬프트 본문·코드는 옮기지 않았다. 아래 수치는 책의 예제 게임 값이며 ai-ps 게임은 다른 값을 쓴다(`design.md`).

## 1. 페이지별 핵심

| 쪽 | 핵심 |

| p126 | 세 함수의 역할 분리(추출/적용/표시). "규칙은 코드가 확정적으로 강제"(LLM이 큰 값을 줘도 클램프, 클리어 보고도 조건 미충족이면 거부). 도구 절 시작: 주사위는 면 수와 난이도를 받아 결과·성공 여부를 돌려줌 |

| p128 | 게임 루프 시작부. 도구 호출 처리 함수(알 수 없는 도구는 오류 결과), 초기 상태 복사, 시스템 프롬프트 + "현재 상태 JSON을 포함한 시작 메시지"로 첫 장면 요청. 호출 파라미터: tools, reasoning 없음, 높은 temperature |
| p129 | 도구 호출은 while 루프, 반복 상한 5. 첫 장면은 배경 묘사라 상태를 갱신하지 않음. 메인 루프: 종료 조건(게임 오버·클리어)까지 입력 받기, 종료어 처리, 매 턴 user 메시지에 현재 상태 JSON + 행동을 함께 전달 |
| p130 | 응답 처리: 파싱 실패 턴은 상태를 바꾸지 않고 안내만 출력(무효 턴). 종료 메시지. temperature 0.9 근거: 묘사가 창의적이어야 함 |
| p131 | 0.9가 Queens의 0.8보다 높은 이유: 다양성을 코드 난수로 대신할 수 없고 문장 자체가 다양해야 함("같은 다양성이라도 어디서 만들지는 문제가 정한다"). 매 턴 상태 JSON 전달 = 세계관 일관성의 첫 장치(히스토리 추론 대신 명시 상태 기준). 도구 루프 상한의 필요. 적용 함수가 범위 제한으로 보호. 작은 결정 2가지: 첫 장면은 상태 미갱신, 파싱 실패 턴은 무효 처리해 형식 오류 하나가 게임을 망치지 않게 함 |

## 2. 전체 설계 결정 요약

### 출력 성격
- 창의적 서술이 목적이라 temperature를 높게 둔다(예제 0.9). 다양성을 코드 난수로 대체할 수 없는 문제에서는 모델 온도가 다양성의 원천이다.
- 응답은 "서술 텍스트 + 상태 변화 JSON"을 한 객체에 담는다. 서술과 상태가 항상 함께 나오고 파싱이 쉽다.
- 설명 가능성·멀티모달은 필요 없다.

### 실행 구조
- 사용자가 루프를 주도하는 멀티턴. 자율 에이전트 루프는 없다.
- 도구는 최소(주사위 1개). 도구 호출은 모델이 결과를 반영해 응답할 때까지 반복하되 상한을 둔다(예제 5회).
- 첫 장면은 배경 묘사이므로 상태를 바꾸지 않는다.

### 운영 제약
- 실시간성이 중요해 스트리밍을 권장한다(5.1 코드는 스트리밍을 구현하지 않음).
- 비용은 중간. 매 턴 상태 JSON을 다시 보내므로 턴당 입력이 일정 크기 이상이다.
- 스토리 실패(어색한 묘사)는 허용, 상태 관리 실패(수치 오염)는 비허용 → 상태 규칙은 전부 코드가 강제.

### 핵심 과제와 책의 대응
| 과제 | 대응 |
|---|---|
| 세계관 일관성 | 시스템 프롬프트에 세계관·규칙 명시, 매 턴 현재 상태 JSON을 user 메시지에 포함(히스토리에서 추론하지 않게), 세계관 밖 입력은 실패로 묘사하되 흐름은 유지 |
| 구조화된 상태 관리 | 변화량(delta) 보고 → 코드가 적용·클램프·아이템 중복 방지·종료 조건 재검증. 기본 소모는 코드만 적용 |
| 히스토리 토큰 관리 | 4분면에 과제로만 명시. 5.1 코드는 messages를 계속 누적하고 자르지 않는다(이후 절에서 다룰 것으로 추정) |

## 3. 상태(JSON) 스키마 아이디어

책의 예제 상태는 `day / time / health / hunger / thirst / inventory / location / game_over / game_clear` 9개 필드다. 여기서 가져갈 원칙:
- **수치는 0~100 정수**, 코드가 클램프한다.
- **파생 규칙은 코드에**(0일 때 패널티, 잠잘 때 회복, 종료 판정).
- **종료 플래그는 코드가 세운다**. LLM의 클리어·게임오버 보고는 "요청"이고 코드가 조건을 재검증한다.
- **응답 JSON은 상태 전체가 아니라 변화량**: 스탯 delta, 아이템 추가/제거, 장소·시간 갱신, 다음 날 여부, 종료 요청.
- 상태 객체에 없는 것: 히스토리, 날씨(프롬프트에만 "변할 수 있다"로 언급, 상태 필드는 아님).

ai-ps 게임의 실제 스키마는 `design.md` 3절.

## 4. 프롬프트 구성 원칙

1. **절 구조 고정**: 역할 한 줄 → 배경 → 세계관(장소·재료·위험) → 스탯 규칙(행동당 변화, 0일 때, 범위) → 진행 규칙(날짜 전환·회복, 확률은 도구 강제, 클리어 조건+필요 아이템) → 입력 검증(불가능한 행동 처리) → 응답 형식(JSON 필드와 의미, 변화량 부호 규칙, 기본 소모는 포함 금지, 수치 예시 1개).
2. **코드가 적용하는 것은 프롬프트에서도 "보고하지 말라"고 명시**해 이중 적용을 막는다.
3. **확률 판정은 도구 사용을 "반드시"로 지시**하고 예시 상황(사냥·낚시·위험 탐험)을 든다.
4. **세계관 밖 입력**: 거부가 아니라 "실패한 행동"으로 묘사, 변화량은 비움(기본 소모는 코드가 적용).
5. 길어지더라도 규칙을 빠짐없이 넣는다. 프롬프트 길이보다 규칙 누락 비용이 크다.
6. 매 턴 user 메시지 = `[현재 상태 JSON] + 플레이어 행동`. 첫 턴 = 상태 JSON + "첫 장면 묘사" 요청.

## 5. 히스토리·토큰 관리

- 책 5.1 범위의 사실: 세계관 일관성은 "상태 JSON 명시 전달"로 확보하고, 히스토리는 누적만 한다(도구 호출·결과 메시지까지 모두 쌓임).
- 따라서 우리 설계가 채워야 할 부분: 최근 N턴만 원문 유지, 그 이전은 코드가 만든 요약(일지)으로 대체, 도구 호출 메시지는 턴이 끝나면 히스토리에서 제거. 상태 JSON이 매 턴 재전달되므로 오래된 턴을 잘라도 상태 일관성은 유지된다는 점이 근거다.

## 6. 스트리밍·실패 허용도

- 스트리밍은 권장 사항이고 5.1 코드에는 없다. JSON 응답과 스트리밍은 충돌한다(JSON이 끝나야 파싱 가능) → 서술을 먼저 보여 주려면 (a) 프레임 단위 의사 스트리밍, (b) 서술/상태 2회 호출, (c) JSON 부분 파싱 중 하나를 골라야 한다. 책은 선택하지 않았다.
- 실패 허용도: 서술 품질 실패는 허용. 형식 실패(JSON 파싱 불가)는 "무효 턴"으로 처리해 상태를 건드리지 않고 다음 입력을 받는다. 도구 반복은 상한으로 끊는다. 상태 오염은 클램프·조건 재검증으로 방지한다.

## 7. 분석 방법

### 읽은 순서와 추출한 것
1. p120 4분면 → 설계 결정의 분류 축(출력·실행·운영·과제)을 먼저 확보했다. 이 축이 2절의 뼈대다.
2. p120 보조·p121 → 게임 규칙과 초기 상태 필드. 필드명과 시작값, 규칙 간 상호작용을 기록했다(3절).
3. p121 보조~p123 → 시스템 프롬프트의 절 구조와 설계 의도 4가지. 본문은 옮기지 않고 절 제목 수준과 "무엇을 왜 넣었는가"만 기록했다(4절).
4. p124~p126 → 상태 코드의 처리 순서(파싱→기본 소모→변화량→패널티→클램프→아이템→장소/시간→게임오버→다음 날→클리어 재검증). 순서 자체가 설계이므로 순서만 기록했다.
5. p126~p127 → 도구의 입력·출력 형태와 "LLM이 못 하는 것을 도구가 대신한다"는 근거.
6. p128~p130 → 루프 구조(첫 장면 → 메인 루프 → 도구 while → 파싱/적용), 호출 파라미터, 무효 턴 처리.
7. p130~p131 → 각 결정의 이유 문단. 2절·6절에 반영했다.

### 다시 볼 필요가 없게 기록한 것(책의 예제 값, 참고용)
- 스탯 시작값 100/80/80, 1일차 아침 해변, 인벤토리 빈 배열.
- 행동당 기본 소모: 허기 −5, 갈증 −7. 둘 중 하나가 0이면 체력 −10씩. 잠: 다음 날·아침·체력 +20(상한 100). 클램프 0~100.
- 클리어: 7일차 이상 + 불 관련 아이템 보유 + LLM의 클리어 보고. 게임 오버: 체력 0(다음 날 회복 전 기준).
- 주사위: 1~면수 균등, 성공 = 결과 ≥ 난이도. 도구 반복 상한 5.
- 호출: tools 지정, reasoning 없음, temperature 0.9(Queens 0.8보다 높음). 모델명은 책 시점 값이라 기록하지 않는다.
- 응답 JSON 필드 9개(서술, 스탯 변화 3, 아이템 추가·제거, 장소, 시간대, 다음 날, 게임오버, 클리어).

### 다시 봐야 하는 경우
- 책의 프롬프트 문장 표현을 참고하고 싶을 때 → p122~p123. (우리 프롬프트는 자체 작성이므로 보통 불필요)
- 상태 적용 순서의 세부(예: 아이템 중복 조건, 게임오버와 다음 날 회복의 선후) 확인 → p124~p125.
- 첫 장면 요청 메시지의 구성과 무효 턴 처리의 정확한 분기 → p128~p130.
- 4분면 그림 원본 → p120. 그 외 그림은 없다.
- 5.1에 없는 내용(히스토리 요약, 스트리밍 구현)은 다음 절 캡처가 생기면 별도 분석한다.
