# 7.1절 자동 리서치 에이전트 분석

출처: 『문제 해결을 위한 AI 에이전트 설계』(한빛미디어) 7.1절, p160~p173. 2026-11-19에 캡처 14장을 한 번 읽고 문제 분석·설계 결정·도구 원칙·루프·한계를 자기 말로 정리했다. 원문 문장·프롬프트 본문·코드는 옮기지 않았다. 아래 수치·모델명은 책 예제의 값이며 ai-ps `/research`는 다른 값을 쓴다(`design.md`). 7.2의 비교표도 같은 캡처 범위(p173)에 있어 함께 실었다.

## 1. 페이지별 핵심

| 쪽 | 핵심 |
|---|---|
| p160 | 문제 분석(1장의 2×2 매트릭스). 정보 수집 자체(검색 실행·페이지 가져오기)는 판단이 개입하지 않는 **규칙 기반 코드**이고, 무엇을 검색할지·어떤 페이지를 읽을지 결정하는 것은 **비정형 텍스트를 읽고 가치를 판단**하는 일이라 제4사분면(LLM의 몫). 수집 정보를 종합해 보고서를 쓰는 것도 제4사분면(여러 비정형 텍스트를 추려 일관된 글로 재구성, 같은 자료라도 매번 조금씩 다름). 출처 추적·참고 자료 목록 붙이기는 정형 데이터의 기록·정리라 제1사분면 |
| p161 | 여기까지는 익숙한 패턴(창의적 판단은 LLM, 규칙 처리는 코드). **새로운 점은 사분면이 아니라 실행 구조**: 작업의 흐름 자체를 LLM이 결정한다. 4장 Queens의 루프는 생성→검증→재생성의 고정 순서였지만, 리서치 루프는 검색할지·읽을지·끝낼지를 매 반복마다 에이전트가 고른다. 자율성 **레벨 3**. 설계 결정은 4장의 세 축을 따른다. 출력은 사람이 읽는 보고서라 자연스럽되 구조가 필요하고(개요·주요 내용·시사점·참고 자료), **설명 가능성**이 핵심 요구다. 모든 주장에 출처를 표기하면 신뢰 확인이 되고 동시에 할루시네이션을 억제한다(자료에 근거해서만 쓰게 강제). 창의성은 낮게 → temperature를 낮춘다. 실행 구조는 **싱글턴**(주제 한 번 입력 → 보고서, 중간 대화 없음; 5·6장의 멀티턴과 대비) |
| p162 | 싱글턴이지만 한 요청 안에서 에이전트가 긴 루프를 돈다(검색·읽기·판단 반복). 3장의 **ReAct**(생각→행동→관찰→재생각)을 프롬프트 유도가 아니라 **Function Calling**으로 안정적으로 구현. 도구는 **search_web**(검색)과 **read_webpage**(본문 읽기) 2종. 2장 이후 도구가 두 개 이상인 첫 프로젝트라 "어떻게 설계해야 에이전트가 잘 선택하는가"가 핵심 주제. 운영: 실시간성은 낮다(사람이 몇 시간 걸릴 일을 몇 분 안에 끝내면 충분; 6장의 0.2초와 정반대). 대신 루프 횟수를 코드가 정하지 않으므로 **반복 상한**으로 비용을 예측 가능하게 만든다(자율성 + 안전장치). 실패 허용도는 **조사 과정 높음**(검색 1~2회 실패는 재시도), **보고서 내용 낮음**(의뢰인이 검증할 시간이 없음; 출처 기반 작성으로 줄이지만 완전히 없애지 못함) |
| p163 | **그림 7-1 설계 결정 요약**(네 칸: 출력의 성격 / 실행의 구조 / 운영의 제약 / 핵심 과제). 개발 환경 준비: `pip install openai python-dotenv ddgs trafilatura`. ddgs는 API 키 없이 검색하지만 비공식 엔진 이용이라 차단·동작 변화 위험 → 프로덕션은 상용 검색 API 권장. trafilatura는 HTML에서 메뉴·광고·댓글·푸터 같은 잡음을 제거하고 본문만 추출(토큰 낭비·품질 저하 방지) |
| p164 | 도구 구현. `search_web(query, max_results=5)`: 결과를 제목·주소·요약이 구분된 문자열로 만들고, 결과 없음·예외도 메시지 문자열로 반환. 연속 검색 차단을 피하려 1초 지연. `read_webpage(url)`: HTML 가져오기·본문 추출 실패도 문자열로 반환, **본문은 4,000자로 절단**. 도구 정의(JSON)는 두 도구의 이름·설명·파라미터를 담고, `description`에 다른 도구와의 관계까지 적는다 |
| p165 | 4,000자 절단의 이유: 수만 자 문서를 통째로 넣으면 입력 토큰이 폭증하고 루프 반복 시 비용이 감당할 수 없게 된다. 조사 목적이라면 앞부분 4,000자로도 핵심 파악이 가능한 경우가 많다(비용·정보량의 트레이드오프). 글자 수 절단은 토큰 수의 대략적 제한일 뿐, 같은 글자 수라도 언어별 토큰 소비량은 다르다 |
| p166~p167 | **도구 설계의 세 원칙(그림 7-2)**: ① description은 사용 설명서(무엇 + 언제 + 다른 도구와의 관계) ② 반환값은 LLM이 읽을 텍스트(프로그램용 객체가 아니라 읽고 판단하기 좋은 형태) ③ 오류도 예외가 아니라 문자열로 반환(예외는 루프를 죽이지만, 메시지는 에이전트가 대처하게 함). 구현: 에이전트 루프의 시스템 프롬프트(작업 방식 4단계 + 조사 노트 규칙) 작성 |
| p168~p170 | `run_research(topic, max_iterations=10)`: 매 반복마다 모델 호출(tools 포함, 온도 0.2, 추론 없음), 응답을 대화에 추가. `tool_calls`는 리스트(한 응답에 독립 검색 여러 개 가능)라 하나씩 실행해 결과를 `tool` 메시지로 붙인다. **종료 조건은 에이전트의 판단**(도구 호출 없이 텍스트로 답하면 조사 완료 신호). **max_iterations=10**은 자율의 한계선: 상한 도달 시 코드가 개입해 "지금까지 수집한 정보를 정리"하도록 요청하고, 마지막 호출에는 **tools를 넘기지 않아** 반드시 정리 응답이 나오게 한다 |
| p171 | 조사와 보고서 작성을 분리. `write_report`는 조사 노트만을 입력으로 받아 개요·주요 내용·시사점·참고 자료 순 마크다운을 만들고, 노트에 없는 사실 금지·각 항목에 근거 URL·참고 자료에 모든 출처를 요구한다. 온도는 0.3(조사 0.2와 용도별 분리) |
| p172 | 분리 이유 두 가지: ① **맥락 크기** — 조사 대화에는 검색 결과·본문이 잔뜩 쌓여 원자료 잡음이 보고서에 섞이기 쉬우므로, 노트로 한 번 압축한 뒤 깨끗한 맥락에서 쓴다(5장의 요약본 교체와 같은 발상) ② **역할 분리** — 조사는 넓게 모으기, 작성은 다듬어 전달하기. 단계별 지시를 따로 주면 프롬프트가 단순해지고 문제 위치를 파악하기 쉽다(6장 파이프라인 장점과 같은 원리). 실행 결과 예: 한국어 검색 → 영어 검색 → 사례 보충 검색 순서를 **코드에 적어두지 않았는데도** 에이전트가 스스로 정했다 |
| p173 | 실행 결과 해설(검색어·횟수·읽을 페이지 전부 에이전트 결정, 주제에 따라 흐름이 달라짐, 같은 주제도 매번 다른 보고서 = 비결정론). **이 에이전트의 한계 4가지**. **7.2 네 개의 에이전트 비교표**(4장부터의 프로젝트를 나란히 정리) |

## 2. 설계 결정 요약(책)

### 출력의 성격
- 사람이 읽는 문서이므로 자연스럽지만 구조가 있다: **개요 → 주요 내용 → 시사점 → 참고 자료**의 마크다운.
- **설명 가능성이 이번 문제의 눈여겨볼 지점**. 게임 묘사·회화 대답에는 근거가 필요 없었지만, 보고서는 읽는 사람이 내용을 신뢰하려면 출처가 어디인지 확인할 수 있어야 한다. 모든 주장에 출처 표기를 출력 요구사항으로 삼는다.
- 출처 표기는 신뢰의 문제이자 **할루시네이션 억제 장치**: 수집 자료에 근거해서만 쓰게 강제하면 지어낼 여지가 줄어든다.
- 창의성은 낮게 유지 → temperature를 낮춘다(책 예제는 조사 0.2, 보고서 0.3).

### 실행의 구조
- **싱글턴**: 주제 한 번 입력 → 보고서. 중간에 대화를 주고받지 않는다(5·6장의 멀티턴과 대비).
- 싱글턴이라고 단순한 것은 아니다. 한 요청 안에서 에이전트가 **긴 루프**를 돌고, 검색·읽기·판단을 여러 번 반복한 뒤 응답이 나온다. 주도권은 에이전트에게 있다.
- 3장의 ReAct(생각·행동·관찰·재생각)과 같은 구조를, 프롬프트 유도가 아니라 **Function Calling**으로 더 안정적으로 구현한다.
- 도구는 **2종**: `search_web`(웹 검색), `read_webpage`(페이지 본문 읽기). 도구가 하나일 때는 쓸지 말지만 판단하면 됐는데, 이제는 **어떤 도구를 쓸지도 판단**해야 한다. 도구 설계가 이 장의 중요한 주제다.

### 운영의 제약
- **실시간성은 낮다**: 리서치는 원래 시간이 걸리는 일. 사람이 몇 시간 걸릴 조사를 몇 분 안에 끝내면 충분하다(6장의 0.2초 다툼과 정반대).
- **비용 상한이 필요하다**: 몇 번의 LLM 호출이 일어날지 코드가 정하지 않으므로, 판단이 이상하게 흐르면 같은 검색을 반복하며 호출이 계속 쌓인다. 반복 횟수에 상한을 두어 최악의 경우도 비용을 예측 가능하게 만든다. 자율성을 높이면서 안전장치를 함께 두는 것.
- **실패 허용도가 갈린다**: 조사 과정은 높음(검색이 한두 번 실패하면 다른 검색어로 재시도), 보고서 내용은 낮음(사실이 아닌 내용이 들어가는 것은 심각 — 조사를 시킨 사람은 검증할 시간이 없어서 시킨 것). 출처 기반 작성이 위험을 줄이지만 완전히 없애지는 못한다.

## 3. 도구 설계의 세 원칙 (그림 7-2)

| 원칙 | 내용 | 책 예제에서 반영된 지점 |
|---|---|---|
| 1. `description`은 사용 설명서 | 무엇을 하는지 + **언제 쓰는지** + **다른 도구와의 관계**를 적는다. 에이전트는 설명을 읽고 어떤 도구를 언제 쓸지 판단한다 | `search_web` 설명에 "자세한 내용이 필요하면 결과 주소를 `read_webpage`로 읽어야 한다" → 두 도구의 조합 순서까지 안내. `read_webpage` 설명에 "검색 결과의 요약만으로 부족할 때" → 사용 시점 명시 |
| 2. 반환값은 LLM이 읽을 텍스트 | 프로그램용 자료 구조가 아니라 **읽고 판단하기 좋은 형태**로 돌려준다. 도구 결과는 대화 메시지로 LLM에게 전달된다 | 검색 결과를 파이썬 객체가 아니라 제목·주소·요약을 구분한 정돈된 문자열로 반환 |
| 3. 오류도 문자열로 반환 | 예외를 던지면 프로그램이 멈추고 루프가 끝난다. 메시지로 반환하면 에이전트가 실패를 인지하고 스스로 대처한다 | 실패 시 "페이지를 가져올 수 없습니다" 같은 문자열 + "다른 페이지를 시도해보세요" 안내(대처 방향 유도). 실패 결과도 다음 행동을 정하는 정보로 활용 |

도구 구현 메모: 검색은 연속 요청 차단을 피하려 호출 사이에 짧은 지연을 둔다. 본문은 4,000자로 자르는데, 이는 비용과 정보량 사이의 트레이드오프이며 글자 수 기준이라 언어에 따라 실제 토큰 소비량은 다르다.

## 4. 에이전트 루프 · 종료 조건 · max_iterations

**시스템 프롬프트의 작업 방식(네 단계)**
1. 주제를 파악하고 무엇을 검색할지 계획한다.
2. `search_web`으로 검색하고, 중요해 보이는 페이지는 `read_webpage`로 직접 읽는다. 검색 결과의 짧은 요약만 보고 판단하지 않는다.
3. 하나의 출처에 의존하지 말고 **서로 다른 출처를 3개 이상** 확인한다.
4. 정보가 충분히 모였다고 판단되면 도구 호출을 멈추고, 수집한 정보를 정리해 응답한다.

**조사 노트 규칙**
- 각 정보를 어느 페이지(URL)에서 얻었는지 반드시 함께 기록한다.
- 페이지에서 확인한 내용만 기록하고, 추측이나 사전 지식으로 보충하지 않는다.

**루프 동작**
- `run_research(topic, max_iterations=10)`: system + user 메시지로 시작해 매 반복마다 모델을 호출한다(tools 포함, 온도 0.2, 추론 없음). 응답 메시지를 그대로 대화에 추가한다.
- `tool_calls`가 **리스트**인 이유: LLM이 한 응답에 도구 호출을 여러 개 담을 수 있다(독립적인 검색 두 개를 한 번에 요청 등). 하나씩 실행해 각 결과를 `tool` 역할 메시지로 대화에 붙인다. 알 수 없는 도구나 실행 예외도 문자열 결과로 처리해 루프가 죽지 않게 한다.

**종료 조건 = 에이전트의 판단**
- 에이전트가 도구를 호출하는 동안 루프는 계속 돈다. 도구 호출 없이 텍스트로 응답하면 "조사를 끝냈다"는 신호다.
- 5장 게임 루프는 사용자가 종료를 입력했고, 4장 생성 루프는 검증 통과라는 코드의 판정이 종료 조건이었다. 이번에는 "정보가 충분한가"라는 판단 자체를 에이전트가 내린다 — 자율성 레벨 3의 모습.

**max_iterations=10**
- 자율에는 한계선을 긋는다. 에이전트 판단이 잘못되어 맴돌아도 반복 상한에 도달하면 **코드가 개입**한다.
- 이때 그냥 멈추지 않고 "조사를 마무리하고 지금까지 수집한 정보를 정리해 주세요"라는 요청을 보내 마무리 짓는다.
- 마지막 호출에는 **tools를 넘기지 않는다**. 도구 정의가 없으면 에이전트는 도구를 호출할 수 없으므로 반드시 정리 응답이 나온다. 자율성은 신뢰하되 안전장치는 코드로 강제한다(4장부터 이어지는 원칙).

## 5. 조사와 보고서 작성을 분리한 이유

조사 루프가 돌려주는 것은 **출처가 달린 조사 노트**이고, 이를 보고서로 다듬는 일은 별도의 호출로 처리한다. 이유는 두 가지다.

1. **맥락의 크기**: 조사 대화에는 검색 결과와 페이지 본문이 잔뜩 쌓여 있다. 이 긴 맥락 위에서 보고서까지 쓰게 하면 원자료의 잡음이 보고서에 섞여들기 쉽다. 조사 노트라는 중간 결과물로 한 번 압축한 뒤 깨끗한 맥락에서 쓰는 편이 품질이 좋다. 5장에서 긴 히스토리를 요약본으로 교체했던 것과 같은 발상이다.
2. **역할의 분리**: 조사는 넓게 모으는 일, 작성은 다듬어 전달하는 일이다. 단계에 맞는 지시를 따로 주면 프롬프트도 단순해지고, 문제가 생겼을 때 어느 단계의 문제인지 파악하기 쉽다. 6장에서 파이프라인의 장점으로 말한 원리다.

이 구조는 **에이전트 루프와 파이프라인의 조합**이다. 조사라는 첫 단계 안에서는 에이전트가 루프를 주도하고, 조사 노트가 나오면 작성이라는 고정된 다음 단계로 넘어간다.

보고서 작성 규칙: 개요·주요 내용·시사점·참고 자료 순으로 구성, 조사 노트에 있는 내용만 사용, 주요 내용 각 항목에 근거 URL 표기, 참고 자료 절에 사용한 모든 출처 나열. 온도는 0.3으로 조사(0.2)와 용도별로 나눈다.

## 6. 이 에이전트의 한계 4가지

1. **조사 품질이 검색 품질에 좌우된다.** 에이전트는 검색 결과에 나온 페이지만 읽을 수 있다. 검색 엔진이 좋은 자료를 보여주지 않으면 좋은 보고서가 나올 수 없다. 광고성 콘텐츠나 저품질 글이 상위에 있으면 그것이 조사의 재료가 된다. 시스템 프롬프트에 출처 신뢰도 기준을 추가할 수는 있지만, 근본적으로는 검색이라는 입구의 품질 문제다.
2. **읽을 수 없는 페이지가 많다.** trafilatura는 정적인 HTML에서 본문을 추출한다. 자바스크립트로 내용을 그려내는 페이지, 로그인이 필요한 페이지, 크롤링을 차단하는 사이트는 읽지 못한다. 에이전트는 오류 메시지를 받고 다른 페이지로 넘어가지만, 가장 좋은 자료가 그 페이지에 있었다면 조사에서 빠진다.
3. **조사의 깊이가 얕다.** 반복 상한 10회 안에서 검색과 읽기를 해야 하므로 확인할 수 있는 출처는 보통 대여섯 개다. 사람의 심층 리서치처럼 참고 문헌을 따라가며 파고들지는 못한다. 상한을 늘리면 깊어지지만 비용도 늘어난다. 어느 수준이 적절한지는 문제의 가치에 달린 설계 결정이다.
4. **출처를 달아도 할루시네이션은 남는다.** 출처 기반 작성을 강제해도 LLM이 페이지 내용을 잘못 요약하거나 두 출처의 내용을 뒤섞는 일이 일어날 수 있다. 출처 표기는 검증을 쉽게 만들어 줄 뿐 내용의 정확성을 보장하지 않는다. 표기된 출처를 열어보면 그런 내용이 없는 경우도 있다. 프롬프트를 다듬는 수준으로 해결되지 않는, 시스템 차원의 대응이 필요한 문제이며 다음 장의 주제다.

## 7. 7.2 네 개의 에이전트 비교표

4장부터 만든 네 에이전트를 나란히 놓은 표(책의 값):

| 구분 | Queens 게임 생성기 | 텍스트 어드벤처 | 영어 회화 연습 | 자동 리서치 |
|---|---|---|---|---|
| 사분면 | 4 + 1 + 3 | 4 + 1 | 4 + 2 + 1 | 4 + 1 |
| 패러다임 | 1.0 + 3.0 | 1.0 + 3.0 | 1.0 + 2.0 + 3.0 | 1.0 + 3.0 |
| 모달리티 | 텍스트 | 텍스트 | 음성 + 텍스트 | 텍스트 |
| 턴 | 싱글턴 | 멀티턴 | 멀티턴 | 싱글턴 |
| 루프 | 프로그램(고정 순서) | 사용자 주도 | 사용자 주도 | 에이전트 주도(자율) |

자동 리서치는 네 프로젝트 중 유일하게 **루프의 주도권이 에이전트**에게 있는 경우다. 나머지는 고정 순서(Queens)나 사용자 주도(어드벤처·회화)다.
