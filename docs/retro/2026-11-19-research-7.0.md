## 잘된 점

- **계약 파일 → 동시 분배 → 44분 안에 운영 배포.** 공통 계약 한 장으로 다섯 워커가 파일 충돌 없이 병렬로 일했고 테스트는 458 → 541개로 늘었다. `ps-glm`을 처음 투입했는데 domain·app을 한 번에 통과시켰다.
- **워커 보고의 질이 좋았다.** `ps-sol`은 키 값을 한 번도 출력하지 않고 길이·패턴만 표로 보고했고, 운영 장애를 실제 workerd로 재현해 수정 전후 표를 냈다. `ps-hf`는 OG 잘림을 지시 밖이라 고치지 않고 "참고(조치 없음)"로 보고했다.
- **선행 리뷰가 실측으로 blocker를 잡았다.** 정규식 처리 시간을 20·40·80KB로 측정해 2차 증가를 수치로 보였다(80KB에 2.2초). 호스트 허용 목록(M1 완화)은 app 연결에 바로 반영됐다.
- **NCP는 사용자 정보가 들어오자 5분 만에 연결됐다.** 올바른 상품명이 주어지니 엔드포인트 탐색·어댑터·병합·테스트까지 한 턴이었다.

## 책임 정리

- **총괄(ps-opus)**: #1·#2·#3·#4·#7·#8·#9. 공통 원인은 "분배보다 판단을 먼저 했다"는 것이다. 판단이 필요하면 `ps-fable`에 묻고 결과를 따르는 것이 사용자가 정한 운영 방식이다(메모리 `opus-low-delegate-judgment`).
- **ps-fable(리뷰)**: #5. "Workers 런타임 호환"을 명시적으로 받고도 `redirect: 'error'`를 통과시켰다. 공식 문서의 `redirect` 지원 모드(`follow`·`manual`)를 확인하지 않고 "문제 없음"에 넣었다. 리뷰 문서의 "확인했고 문제 없는 것" 절은 근거 없는 항목을 포함하면 안 된다.
- **ps-sol(구현)**: #5의 1차 원인. 다만 인계 문서에 "Workers 호환"을 Node 표준 API 사용 여부로만 판단했다고 적었고, 장애 재현·수정은 5분 만에 끝냈다.

1. 총괄 역할을 "분배·감시·병합·릴리스·배포"로 좁히고 전역 스킬과 프로젝트 문서를 일치시킨다. 조사·판독·탐색도 워커에 보낸다.
2. 세션 시작 체크리스트(자기 라벨 → 기존 패널 확인 → 워커 열기 → 계약 → 첫 지시)와 "요청 범위 / 범위 밖 제안" 분리를 지시 템플릿에 넣는다.
3. 첫 마일스톤은 "사용자가 로컬에서 돌려볼 수 있는 상태". 하드닝·OG·스크립트는 그다음 패치 버전.
4. 비밀키·외부 계정의 용도는 사용자에게 묻는다. 탐색 호출로 대체하지 않는다.
5. Workers 런타임 검증 두 겹(금지 옵션 arch 테스트 + workerd slow 테스트)과 `docs/providers.md` 호환 표.
6. 버전 규칙(책 장 번호 = 메이저)을 문서와 `release.mjs`에 넣는다.
7. 리뷰 blocker를 들고 배포하면 보고·커밋에 적고 다음 패치의 첫 항목으로 올린다.
